\chapter{Case Study: Real-Time Fraud Detection for Card Payments}
\label{cha:case-study}

This chapter applies the registry and the resolution ladder to a retail-banking scenario: a
card-payment authorisation workflow that screens each transaction for fraud before it is settled.
It extends the \texttt{FraudPipeline} of Section~\ref{sec:developer-workflow} and is illustrative,
not a production deployment. It was deployed and run on an AWS test account and on a GCP project;
a deployment to a production AWS account is only described.

Section~\ref{sec:case-scenario} states the requirements, Section~\ref{sec:case-design} defines the
workflow, Section~\ref{sec:case-deployment} follows the ladder through deployments to two accounts
and two providers, Section~\ref{sec:case-artifacts} reports the two runs, and
Section~\ref{sec:case-discussion} discusses the scenario's limits.

\section{Scenario and Requirements}
\label{sec:case-scenario}

A bank authorises card payments through a workflow. Two internal functions, owned by the fraud
team, score each transaction: \texttt{fraud-check} flags known fraud patterns, and
\texttt{risk-score} computes a numeric risk score. An external call then reports the decision to
the core banking system, which has its own release cycle and is not managed through the registry.
Three requirements motivate the integration:

\begin{itemize}
    \item \textbf{One workflow, several accounts.} If development, testing and production are
    separate cloud accounts, a function has a different endpoint in each (its ARN contains the
    account ID). With endpoints in the definition, every promotion would mean deploying the
    functions and editing the workflow by hand (Section~\ref{sec:int_cha_int_uni_multi}).
    \item \textbf{An exit strategy.} The Digital Operational Resilience Act (DORA) requires EU
    financial entities to have exit strategies for ICT services supporting critical or important
    functions, and to assess ICT concentration risk~\cite[Arts.~28(8) and~29]{dora2022}. Exiting a
    provider is easier if the workflow and its functions can be deployed elsewhere.
    \item \textbf{Auditability of bindings.} Change management needs a record of the endpoint each
    deployment was bound to. The registry gives only the current binding and, in
    \texttt{updatedAt}, the time of the last write (Section~\ref{sec:dsl-extensions}), not which
    deployment wrote each entry (Section~\ref{sec:case-discussion}).
\end{itemize}

\section{Workflow Design}
\label{sec:case-design}

The complete \texttt{PaymentAuthorization} workflow is Listing~\ref{lst:case-payment-workflow}, in
Appendix~\ref{app:listings}. Listing~\ref{lst:case-payment-excerpt} shows its two internal calls,
whose endpoints are resolved at deployment time (Section~\ref{subsec:endpoint-resolution}). Unlike
the partner API of Listing~\ref{lst:wf-external-part}, both functions belong to the bank, so they
are internal. A \texttt{switch} step, \texttt{decision}, jumps to \texttt{decline-transaction} if
the transaction was flagged or its score exceeds 75, and otherwise to
\texttt{approve-transaction}. Both branches record the outcome and reach
\texttt{report-decision}, an external call to core banking that sends the transaction as the body
and the decision as a query parameter.

\begin{lstlisting}[language=Kotlin,caption={The two internal scoring calls of \texttt{PaymentAuthorization} (excerpt of Listing~\ref{lst:case-payment-workflow}).},label={lst:case-payment-excerpt},basicstyle=\ttfamily\small,breaklines=false]
step {
  name("fraud-check")
  description("Flag transactions that match known fraud patterns")
  context(call {
    method(POST)
    internalFunction("fraud-check", "./deploy/fraud-check.json")
    query("amount" to variable("transaction.amount"),
      "country" to variable("transaction.country"))
    result("fraudResult")
  })
},
step {
  name("risk-score")
  description("Score the transaction from its features")
  context(call {
    method(POST)
    internalFunction("risk-score", "./deploy/risk-score.json")
    query("amount" to variable("transaction.amount"))
    result("riskResult")
  })
},
\end{lstlisting}

Two choices keep the definition valid on both providers. The scoring calls pass their inputs as
query parameters, since on AWS an internal call cannot carry a body
(Section~\ref{sec:runtime-invocation}) and a Cloud Workflows query value cannot be a map. And the
conditions name a result field with \texttt{withKey}, which each renderer turns into its provider's
path. The workflow names no provider, region or endpoint: these come from the descriptors and the
choice of deployer.

\section{Deploying Across Accounts and Providers}
\label{sec:case-deployment}

\paragraph{AWS test account.} Neither function exists yet. The ladder reaches Level~3 for both
calls (Section~\ref{sec:walkthrough}), QuickFaaS deploys them as Lambda functions
(Figure~\ref{fig:aws-deploy-level3}), their ARNs are registered, and the state machine is deployed.

\paragraph{AWS production account.} The workflow is unchanged; only the descriptors change, to name
the production bucket (and, optionally, role). The deployment uses its own registry file (the
deployers accept a registry path), bootstrapped from the production account, and Level~3 deploys
both functions there. No endpoint is copied between accounts. The registry must not be shared: a
test-account entry would fail validation in production, be treated as stale, and abort the
deployment (Section~\ref{sec:walkthrough}). This deployment was not run.

\paragraph{GCP.} For the exit strategy, the same workflow is deployed with GCP descriptors and the
GCP deployer. The GCP registry is bootstrapped separately, both calls miss at Levels~1 and~2, and
Level~3 deploys Cloud Run functions (Section~\ref{subsec:gcp-cloud-run-functions}) from the same
ZIP artifact (Section~\ref{sec:background_quickfaas}). The same \texttt{functionRef} resolves to an
ARN on AWS and to a \texttt{run.app} URL on GCP, both stored in the \texttt{url} field, so the
workflow definition does not change.

\section{What the Deployments Produce}
\label{sec:case-artifacts}

Both deployments were run on 28 September 2026; the workflow, functions, scripts and logs are in
the repository folders \texttt{case-study-aws} and \texttt{case-study-gcp}. Both runs differed from
Listing~\ref{lst:case-payment-workflow} in two ways. The internal references were region-qualified
(\texttt{"eu-west-1/fraud-check"}, \texttt{"europe-west1/fraud-check"}); on GCP this was necessary,
because one region of the project refuses Cloud Run lookups and a bare reference would abort at
Level~2 (Section~\ref{subsec:validation-error-semantics}). And \texttt{report-decision} called a
stub of core banking, deployed outside the ladder.

\paragraph{AWS.} The stub was a Lambda function behind an API Gateway HTTP API, created with the
AWS CLI: the renderer turns an external call into an \texttt{apigateway:invoke} task, and a

deployment bootstrapped the registry with the six functions already in the account and reached
Level~3 for both scoring calls: about 17~seconds per function, 48~seconds in all. A second
deployment bound both calls at Level~1, deployed nothing, took about 1.5~seconds, and left the

\section{Discussion}
\label{sec:case-discussion}

Promoting the workflow across accounts and providers needs no edit to its definition. Updating the
fraud model is different: a retrained \texttt{fraud-check} redeployed in place keeps its endpoint
(Section~\ref{sec:resolution-cascade}), so the workflow calls it without being redeployed, but a
workflow deployment never deploys the new model itself (Section~\ref{sec:concl-critical}).

\paragraph{Renderer defects fixed.} Rendering the workflow for AWS exposed two defects in
OmniFlow's AWS renderer, which this work fixed. An \texttt{assign} became a \texttt{Pass} state
whose \texttt{Result} replaced the whole state, losing the transaction before
\texttt{report-decision}. A single-variable \texttt{assign} now writes only that variable
(\texttt{"Result": "approved"}, \texttt{"ResultPath": "\$.decision"}, or an \texttt{InputPath} when
the value is a variable). A multi-variable \texttt{assign} still replaces the state, since a
JSONPath \texttt{ResultPath} writes one place; Cloud Workflows has no such limit. Second, the query
parameters of a Lambda call were wrapped in \texttt{States.Array}, as \texttt{apigateway:invoke}
requires, so a hook received \texttt{"[120]"}; they are now plain strings in the Lambda payload.

\paragraph{Limits found on the live providers.}
\begin{enumerate}
  \item A bare reference assumes every region can be queried. Where some regions are closed by
  policy, it aborts, and the region-qualified form uses provider-specific region names, so the
  definition no longer deploys unchanged to the other provider.
  \item OmniFlow's deployers only create workflows: redeploying means deleting first.
  \item The two renderers expect a literal host in different forms (with a scheme for Cloud
  Workflows, without one for API Gateway), so external calls are not portable.
  \item Function source is not portable: a GCP hook receives request and response objects, while
  the AWS template passes the query parameters as a map and expects a return value, so each scoring
  function was written once per provider.
  \item QuickFaaS's GCP adapter accepts a JSON body only for the exact content type
  \texttt{application/\allowbreak json}, and Cloud Workflows adds a charset, so the GCP stub read the body
  itself.
\end{enumerate}

The scenario remains illustrative: an unguarded registry and broad, automatically granted IAM
roles (Section~\ref{sec:concl-critical}) are not controls a bank would accept for a function that
screens payment data. The hardening needed is set out in Section~\ref{sec:concl-future}.
