\chapter{Serverless Portability: Background and State of the Art}
\label{cha:background}

This chapter has two parts. Section~\ref{sec:background} establishes the technical foundation for
the proposed integration. It first presents the two layers the work builds on, Serverless Computing
and Function-as-a-Service (FaaS), and the workflow layer that orchestrates the resulting functions,
highlighting in each the form of vendor lock-in that motivates this work. It then presents the two
base technologies this dissertation extends: \textbf{QuickFaaS}, which handles the portable
deployment of compute units, and \textbf{OmniFlow}, which manages the portable definition of
orchestration logic. Section~\ref{ch:related-works} turns to the state of the art. It reviews
related research and existing industry tools, and identifies the gap in unified workflow
orchestration that this work aims to close.

\section{Background}
\label{sec:background}

\subsection{Serverless Computing and FaaS}
\label{sec:serverless_computing_faas}
In serverless computing, the cloud provider allocates resources, patches the operating system and
scales the infrastructure. Users are charged only for the time their code runs, not for idle
capacity~\cite{serverlessComputing}.

Function-as-a-Service (FaaS) is the main form of the serverless model. It enables developers to deploy single-purpose, stateless functions that are triggered by specific events (e.g., HTTP requests, database changes). The lack of standardisation across providers (e.g., AWS Lambda, Google Cloud Functions, Azure Functions) exposes FaaS applications to vendor lock-in, as function code often becomes tightly coupled to provider-specific SDKs and deployment artifacts~\cite{rodrigues2022quickfaas}.

This coupling manifests along two independent axes, both relevant to this dissertation. The first
is the \emph{programming model}: each provider defines its own function signature and request/response
types, so the same logic must be rewritten per provider unless an abstraction hides those
differences, which is the problem QuickFaaS addresses with its uniform hook/template model. The
second is
the \emph{packaging and deployment} axis: providers accept code through different packaging
mechanisms, with different naming, permission and trigger conventions, which QuickFaaS addresses
as described in Section~\ref{sec:background_quickfaas}. Beyond portability, the statelessness and
event-driven nature of FaaS also shape how functions are \emph{composed}. A function holds no state
between invocations and cannot directly call another, so non-trivial applications must move
their control flow and data flow into an external orchestrator, the workflow layer discussed next,
rather than encode them inside the functions themselves~\cite{serverlessComputing}.

\subsection{Workflows and Orchestration}
\label{sec:workflows}

A \textit{workflow} describes how a process is executed as a sequence of steps, typically representing a business or operational procedure. In cloud environments, workflows are commonly modelled as \textit{state machines}, where each state performs a unit of work, makes a decision or controls execution flow, while passing data between states~\cite{aws_stepfunctions_concepts}. This is the layer the previous section pointed to, where the control flow, data flow and error handling of a multi-function application live~\cite{sebsflow_arxiv}.

Workflow systems typically provide support for:
\begin{itemize}
	\item \textbf{Control-flow}, such as sequential execution, conditional branching, parallelism, retries and waiting states;
	\item \textbf{Data-flow}, allowing structured data to be passed and transformed between steps;
	\item \textbf{Observability}, such as execution tracking and inspection of intermediate results.
\end{itemize}

Major cloud providers offer managed services for this role, notably AWS Step Functions and Google Cloud Workflows~\cite{aws_stepfunctions_concepts,gcp_workflows_overview}. They are integrated with their provider's FaaS platform, but the logic defining how tasks interact is bound to provider-specific orchestration languages and schemas. This creates a second layer of vendor lock-in, distinct from the code-level one described above: workflow definitions must often be rewritten when moving to a different workflow engine or provider. That limitation has motivated portable, vendor-neutral workflow specifications, which decouple workflow definitions from a specific execution backend and improve interoperability across platforms~\cite{serverlessWorkflowSpec}.

\subsection{QuickFaaS: Portable Function Deployment}
\label{sec:background_quickfaas}
QuickFaaS is a tool that lets developers write a function once and deploy it to several cloud
providers without changing its source code, which removes code-level vendor
lock-in~\cite{rodrigues2022quickfaas}. It is a self-contained desktop application written in Kotlin~\cite{kotlin_lang}, with a
user interface built on Compose for Desktop~\cite{compose_multiplatform}. It also has a headless
entry point that deploys the function described by a JSON deployment descriptor, which is the
entry point this work uses.

\subsubsection{Uniform Programming Model}
To achieve portability, QuickFaaS introduces a Uniform Programming Model that abstracts the differences between provider-specific function signatures (e.g., AWS Lambda's \texttt{Context} vs. GCP's \texttt{HttpRequest}). This model relies on the Template Method Design Pattern:

\begin{itemize}
	\item \textbf{Hook function:} Developers implement a single, cloud-agnostic interface (the "Hook"). This interface uses generic request/response objects (e.g., \texttt{HttpRequestQf}) that are decoupled from any specific vendor SDK.
	\item \textbf{Template function:} QuickFaaS maintains a set of ``Template Functions'' for each supported provider. These templates are wrappers: they are the entry points the cloud provider invokes. Upon invocation, the template adapts the provider-specific data into the generic format and calls the developer's Hook logic.
\end{itemize}

\subsubsection{FaaS Deployment Model: The ZIP Strategy}
While different cloud providers offer various methods for deploying code (such as inline editing, container images, or git syncing), the upload of a compressed source archive (ZIP) is the lowest common denominator supported by AWS, Google Cloud and Azure. By standardising on this format, QuickFaaS does not have to build or manage containers on the user's machine, which keeps the tool light.

For a Java function on Google Cloud Platform (GCP), QuickFaaS places the developer's hook (e.g.,
\texttt{MyFunctionClass.java}) in a temporary project next to the provider's template (here
\texttt{GcpHttpTemplate.java}, the entry point for HTTP events) and the QuickFaaS libraries,
packages it with Maven, and zips the result. It then uploads the archive to the Cloud Storage
bucket named in the deployment descriptor (the \texttt{bucket} field of
Listing~\ref{lst:quickfaas_json_config})~\cite{GCP_bucket}, from which the provider builds and
provisions the function.

On GCP, the original QuickFaaS provisions a \emph{first-generation} Cloud Function, reachable at
\texttt{https://\allowbreak <region>-\allowbreak <project-id>.\allowbreak cloudfunctions.\allowbreak net/\allowbreak <name>},
which, unlike a second-generation function, is not a Cloud Run
service~\cite{gcpFunctionsVersionComparison}. (Google now calls the two generations \emph{Cloud
Run function (1st gen)} and \emph{Cloud Run function}. This dissertation keeps the generation
names, which distinguish the two APIs the code calls.) Because the proposed Function Registry
validates and discovers GCP functions through the Cloud Run API, this work moves QuickFaaS's GCP
provider to second-generation functions (Section~\ref{subsec:gcp-cloud-run-functions}).


\subsubsection{QuickFaaS function deployment example}
\label{subsec:quickfaas-example}
To deploy a function to Google Cloud Platform (GCP) with the original QuickFaaS, the developer
provisions credentials and writes a JSON configuration, in the following steps.

\begin{enumerate}
	\item \textbf{Credential Provisioning:} The developer must first create an OAuth 2.0 client within the Google Cloud Console to retrieve the Client ID and Client Secret. This step requires registering the authorised redirect URL (e.g.,
\url{http://localhost:8080/quickfaas/gcp/callback}) and the authorised JavaScript origins used by
the authentication flow.
	
	\item \textbf{Authentication Configuration:} The retrieved Client ID and Secret are injected into the authentication module. The developer runs the auxiliary Node.js server, which carries out the OAuth flow and returns the \texttt{access\_token} required for deployment.
	
	\item \textbf{Deployment Definition:} Once the token is obtained, the developer populates the deployment file, \texttt{func-deployment.json} (Listing \ref{lst:quickfaas_json_config}). This JSON object defines the target infrastructure, including the  \texttt{cloudProvider}, the \texttt{project} ID and the \texttt{accessToken} the developer acquired from the authentication mechanism. It also specifies function metadata such as the \texttt{runtime} (e.g., \texttt{java17}) and trigger type.
	Lastly, \texttt{functionFile} gives the location of the cloud-agnostic function file the
	developer wishes to deploy.
	Inside \texttt{function}, \texttt{location} is the region the function is created in, and
	\texttt{bucket} names the Cloud Storage bucket used to stage the packaged source. The two
	trailing fields (extra Maven dependencies and runtime configuration) are optional and left empty
	here.
 
	
	\begin{lstlisting}[language=json, caption={Configuration JSON for QuickFaaS function deployment.}, label={lst:quickfaas_json_config}]
		{
			"cloudProvider": "gcp",
			"accessToken": "access-token-received",
			"project": "tfm26-509910",
			"function": {
				"name": "quickfaas-test-fn",
				"location": "europe-west1",
				"bucket": "tfm26-quickfaas-deploy",
				"runtime": "java17",
				"trigger": {
					"type": "http"
				}
			},
			"functionFile": "./MyFunctionClass.java",
			"dependenciesFile": "",
			"configurationsFile": ""
		}
	\end{lstlisting}
	
	\item \textbf{Hook Function Implementation:} The developer implements the business logic by creating a cloud-agnostic class (e.g., \texttt{MyFunctionClass.java}), as shown in Listing \ref{lst:hook_function}. This class uses the generic QuickFaaS interfaces, such as \texttt{HttpRequestQf} and \texttt{HttpResponseQf}, which decouple the code from provider-specific SDKs.
	
	\begin{lstlisting}[language=Java, caption={Cloud-agnostic hook function implementation.}, label={lst:hook_function}]
	import quickfaas.triggers.http.HttpRequestQf;
	import quickfaas.triggers.http.HttpResponseQf;
	
	public class MyFunctionClass {
		
		public void myFunction(HttpRequestQf req, HttpResponseQf res) { 
			res.send(200, "Hello world!"); 
		}
	}
	\end{lstlisting}
	
	\item \textbf{Deployment and Verification:} Finally, the system packages the artifacts and uses the Google Cloud APIs to provision the function. A successful deployment is confirmed via the terminal output and the Google Cloud Console.
	
	
	To finalise the process, the developer grants public access permissions, retrieves the generated HTTP Trigger URL and verifies the execution.

\end{enumerate}
\subsection{OmniFlow: Portable Workflow Orchestration}
\label{sec:background_omniflow}

OmniFlow is a Kotlin library and Domain-Specific Language (DSL) for defining serverless workflows independently of a specific provider workflow schema. The developer writes the workflow once using the OmniFlow DSL and the library translates that abstract definition into the workflow format required by a chosen cloud provider (e.g., Google Cloud Workflows) and deploys it through the provider APIs. By separating \emph{workflow logic} from \emph{provider-specific workflow definitions}, OmniFlow aims to reduce orchestration-level lock-in and make workflow specifications easier to maintain over time~\cite{costa2023omniflow,silva2025advanced}.

\subsubsection{Components Overview}
OmniFlow is designed as a client-side library integrated into the developer’s application, organised in four components that run in sequence~\cite{silva2025advanced}:

\begin{enumerate}
	\item \textbf{Domain-Specific Language (DSL):} the developer-facing interface used to define workflows in Kotlin. OmniFlow relies on Kotlin’s \emph{type-safe builder} style for declaring workflow metadata and steps~\cite{type-safe_builders}.

	\item \textbf{Internal Model:} the DSL constructs an internal, provider-agnostic representation of the workflow. Internally, workflows are represented as a \emph{hierarchical tree} of nodes: the workflow is the root node and each step corresponds to a child node, where some step types may contain nested child steps~\cite{silva2025advanced}. This tree-based representation is the basis for workflow traversal and rendering.

	\item \textbf{Renderer:} the renderer traverses the internal model and produces the provider-specific workflow artifact. OmniFlow performs this traversal using a depth-first search (DFS) over the workflow tree so that steps are rendered in a predictable order. Rendering is organised around the \texttt{NodeRenderer} abstraction: for each node type, a corresponding renderer is selected (via a strategy-based matching mechanism) and invoked during traversal. Rendering follows a begin/end discipline, with a rendering context propagated through the traversal, so that nested steps become correctly scoped provider artifacts~\cite{silva2025advanced}. The resulting output is typically a textual artifact (e.g., YAML for Google Cloud Workflows) suitable for deployment.

	\item \textbf{Deployment Services:} after rendering, a provider adapter is responsible for deploying the generated workflow definition to the chosen cloud provider’s workflow service (e.g., by invoking the provider API/SDK). From the developer perspective, this stage turns the rendered artifact into an executable workflow resource managed by the cloud provider~\cite{costa2023omniflow}.
\end{enumerate}

\subsubsection{Workflow Entity Model}
OmniFlow models a workflow as a root \textbf{Workflow} entity that is \emph{composed of} one or more steps.
At the DSL level, the workflow root typically includes a \texttt{name}, a \texttt{description}, an input variable and a result variable~\cite{silva2025advanced}. OmniFlow's model captures these as two entities: input, representing the data received by the workflow, and output, representing the value returned at the end of execution. A workflow therefore \emph{receives} exactly one input and \emph{returns} exactly one output in each execution.

Each \textbf{Step} represents a unit of behaviour inside the workflow. A step belongs to one of four disjoint categories:

\begin{itemize}
  \item \textbf{Execution Step}: steps that perform concrete work such as HTTP calls or variable assignments (for example, the Call and Assign constructs in the OmniFlow DSL).
  \item \textbf{Conditional Step}: steps that select between alternative branches based on one or more conditions (corresponding to Switch-like constructs).
  \item \textbf{Iteration Step}: steps that repeatedly execute a nested block of steps over a range or collection.
  \item \textbf{Parallel Step}: steps that execute multiple branches concurrently.
\end{itemize}

In the DSL, every step has a \texttt{name}, a \texttt{description} and a \emph{context} that holds
the details of its category: for an execution step, the HTTP method, host and path or the variable
assignments; for the others, the nested branches or bodies to execute.


\subsubsection{Example: Function Chaining}
Listing~\ref{lst:omniflow_chain} illustrates a simple function-chaining pattern in the OmniFlow
DSL, where the output of one step becomes the input of the next through workflow variables. The
workflow declares its input through \texttt{params}. The first step is a \texttt{call}: an HTTP
\texttt{POST} to a literal \texttt{host} and \texttt{path}, whose body is taken from the input and
whose response is stored in the variable \texttt{firstResult} by \texttt{result}. The second step
is an \texttt{assign} that copies the body of that response into \texttt{processedData}, which the
workflow returns as its output.

\begin{lstlisting}[language=Kotlin, caption={OmniFlow Function Chaining Definition.}, label={lst:omniflow_chain}]
val ChainWorkflow = workflow {
  name("FunctionChain")
  description("Sequential execution of cloud functions")
  params("args")
  steps(
    step {
      name("first-call")
      description("Send the input data to the processing API")
      context(
        call {
          method(POST)
          host("example-api.com")
          path("/v1/process")
          body(variable("args.data"))
          result("firstResult")
        }
      )
    },
    step {
      name("process-logic")
      description("Keep the body of the first response")
      context(
        assign {
          variables(variable("processedData") equalTo variable("firstResult.body"))
        }
      )
    }
  )
  result("processedData")
}
\end{lstlisting}

A practical limitation follows from this design: OmniFlow call steps require concrete invocation
targets (e.g., \texttt{host} and \texttt{path}) to be known at definition or deployment
time~\cite{silva2025advanced}, so the functions they call must be deployed first and their
endpoints copied into the definition. This is the manual synchronisation described in
Section~\ref{sec:int_cha_int_uni_multi}, which the proposed solution removes.

\section{Related Work}
\label{ch:related-works}

The proposed integration between \textit{OmniFlow} and \textit{QuickFaaS} sits at the intersection of two problem areas: (i) composing and deploying workflows without being forced to embed provider-specific workflow specifications and (ii) deploying cloud functions with reduced provider coupling.
Although each deployment target in this dissertation is a \emph{single provider at a time} (Section~\ref{sec:int_cha_int_uni_multi}), portability concerns remain relevant because developers still want to avoid hard-coding endpoints and to preserve the ability to migrate or re-deploy the same application in another provider with minimal changes.

This section reviews the tools, frameworks and methods surveyed in the QuickFaaS
publication~\cite{rodrigues2022quickfaas} and in the OmniFlow
reports~\cite{costa2023omniflow,silva2025advanced}, together with more recent work, and positions
them relative to the objectives of this thesis. They fall into five groups: tooling that automates
deployment through templates or Infrastructure-as-Code (IaC) specifications; portable execution layers
and code transformation to FaaS; methods that measure portability instead of providing it;
workflow composition and orchestration frameworks; and service registries, which map logical
names to endpoints as the Function Registry does. Each group is discussed in turn, showing why
none of them, in isolation, provides the combined behaviour targeted by the OmniFlow--QuickFaaS
integration.

\subsection{Infrastructure-as-Code and Deployment-Oriented Tooling}

A first family of approaches focuses on automating resource deployment and configuration through templates or IaC specifications.

\textbf{AWS CloudFormation}~\cite{awsCloudFormation} is a provider-specific modelling tool. Its resource model belongs to AWS, so the same deployment on another provider requires different tooling and specifications.

\textbf{Terraform}~\cite{terraform} manages infrastructure on many providers with the same tool. However, deploying FaaS resources still tends to be provider-specific in practice: function packaging conventions, configuration resources, permissions and event bindings must be encoded using provider-specific parameters. As a result, Terraform automates deployments but does not, by itself, provide a uniform function development and invocation model.

\textbf{Serverless Framework}~\cite{serverlessFramework} also provides infrastructure automation using YAML for app-centric definitions. Although it reduces operational effort, it still describes provider-specific services and event types and portability depends on the availability and maturity of plugins for each provider.

\textbf{Pulumi}~\cite{pulumi} takes a different approach by expressing infrastructure using general-purpose programming languages. It also explores serverless-specific abstractions such as \textit{Magic Functions}~\cite{pulumiMagicFunctions} and higher-level constructs through the \textit{Cloud Framework}~\cite{pulumiCloudFramework} and the \texttt{@pulumi/cloud} package~\cite{pulumiCloudPkg}. These abstractions move toward a more uniform experience but practical portability remains constrained by provider support coverage and by the fact that many real-world triggers, permissions and operational configurations remain provider-specific.

The \textbf{AWS Cloud Development Kit (CDK)}~\cite{awsCdk} also defines infrastructure in
general-purpose languages, among them Java, and is the closest in style to OmniFlow's Kotlin DSL.
A CDK application, however, is synthesised into a CloudFormation template and deployed through
CloudFormation, so it inherits that service's resource model and is limited to AWS.

\textbf{CODE}~\cite{ristov2024code} is a more recent framework in this family, addressing
\emph{federated FaaS}: running the same function across several regions of several providers.
Following a ``code once, deploy everywhere'' principle, its DSL places the function at the top of a
three-level hierarchy (function, then providers, then regions). One declaration therefore covers
every target instead of being repeated per provider and per region. The authors report up to
9.23$\times$ fewer lines of code than Terraform or the Serverless Framework. A unified storage
library backs this DSL: one command uploads a deployment package to, or copies it between, the
storage services of AWS and GCP, so a function can be deployed directly from whichever provider's
storage already holds it, with no provider-specific upload code. CODE therefore shares this
thesis's ambition for the \textit{function} half of the problem, on the same two providers. It
deploys the functions a workflow invokes, however, not the workflow itself: the authors list the
automatic deployment of workflows written in their own choreography language, on top of CODE, as
future work. That remaining step is what this dissertation addresses: a portable workflow
definition whose function references are turned into concrete endpoints as the workflow is
deployed.

These tools also resolve, at deployment time, the endpoint through which a workflow calls a
function. The workflow definition names the function through an expression that the deployment
engine replaces with the function's identifier once it exists. In AWS SAM, for example, the
\texttt{DefinitionSubstitutions} of a state machine can map a placeholder to
\texttt{!GetAtt MyFunction.Arn}, the Amazon Resource Name (ARN) of a function declared in the same
template~\cite{awsSamStateMachine}. The Step Functions plugin for the Serverless Framework and
Terraform offer equivalent references~\cite{serverlessStepFunctionsPlugin,terraformSfnStateMachine}.
Each such reference is also an implicit dependency, so the function is created before the
workflow that names it~\cite{awsCloudFormationDependsOn,terraformReferences}, and Pulumi orders
resources in the same way~\cite{pulumiInputsOutputs}. This is the same static binding performed by
the resolution ladder proposed in this dissertation (Section~\ref{sec:resolution-cascade}). These
tools also update a function whose code changed, which this work does not. Conversely, they bind a
workflow only to functions declared or explicitly referenced in the same template or
configuration. Terraform and Pulumi can look up a function deployed by other means, but only
through an explicit data source that names it, in the region the configuration
targets~\cite{terraformLambdaDataSource,pulumiLambdaGetFunction}. The resolution ladder, by
contrast, searches the provider's regions for a function it was only given the name of, and
deploys it when it is absent.
What none of them offers is a workflow definition independent of the provider: the state machine is
written in the Amazon States Language, and a GCP workflow would be a separate definition in another
language, with its own references to its own functions.

\subsection{Portable Execution Layers and Code Transformation to FaaS}

A second family either introduces a portable runtime layer or attempts to automatically transform existing code into a FaaS-compatible format.

\textbf{OpenFaaS~\cite{openFaaS}} provides a unified experience for deploying functions on top of containers and orchestration platforms, supported by language templates~\cite{openFaaSTemplates} and a set of trigger mechanisms~\cite{openFaaSTriggers}. This enables functions to run in different environments without changing code, but it creates a parallel FaaS platform ``on top of'' container orchestration. Direct integration with provider-native event sources may be limited, which often leads to HTTP-centric invocation patterns rather than native event bindings.

Regarding automated conversion, Spillner presents work on transforming Python applications into FaaS deployments~\cite{spillner2017pythonfaas} (with a tool its author calls \textit{Lambada}) and Spillner and Dorodko explore Java analysis and transformation into AWS Lambda functions~\cite{spillnerDorodko2017javaLambda}. These approaches are relevant because they attempt to lower the barrier to adoption by converting existing code. However, they are typically anchored to a specific target platform (e.g., AWS Lambda) and automated rewriting can introduce execution overhead and constraints that are difficult to generalise across providers.

In summary, these approaches either (i) replace the provider runtime with a portable runtime layer or (ii) generate provider-specific function artifacts. Neither directly matches the intended goal of this thesis, where functions are still deployed to the providers' own FaaS services but development and orchestration artifacts should remain as provider-agnostic as possible.

\subsection{Assessing Portability Instead of Enabling It}

A third group steps back from enabling portability to \textit{measuring} it. The
\textbf{SEAPORT} method~\cite{yussupov2020seaport} proposes an automated way to assess the
portability of serverless applications (or orchestration tools) against a target provider by
transforming deployment models into a canonical representation (CASE).
This is valuable for decision support and for identifying portability blockers but it does not directly provide a deployment mechanism that \textit{produces} portable artifacts. In other words, it helps explain \textit{how portable} something is, not necessarily \textit{how to make it portable}.

\subsection{Workflow Composition and Orchestration Frameworks}

A fourth family focuses on function composition, workflow execution efficiency and workflow management models.

\textbf{FaaSFlow}~\cite{li2022faasflow} is motivated by performance and efficiency problems in serverless workflow execution. Its core contribution is architectural, shifting scheduling responsibilities away from a central master to worker-side logic and reducing data movement overhead through mechanisms such as adaptive storage. This matters for \textit{runtime efficiency}, but it is not primarily a workflow deployment portability approach.

\textbf{Triggerflow}~\cite{garciaLopez2020triggerflow} provides an event/trigger-based orchestration architecture, combining a front-end API for workflow-related definitions with a trigger processing service following an event-condition-action style. This addresses workflow \textit{runtime} management (including persistence and orchestration behaviour). Compared to OmniFlow, Triggerflow can be interpreted as a generic workflow control plane that operates as its own orchestration system rather than generating artifacts for a provider-native workflow service.

\textbf{AFCL} and \textbf{xAFCL} come from the same group as CODE. AFCL is a YAML-based language
for serverless workflows, which its authors call function choreographies~\cite{ristov2021afcl}, and
xAFCL is an enactment engine that runs the functions of one choreography across several FaaS
systems at once, among them AWS Lambda and Google Cloud Functions~\cite{ristov2023xafcl}. This is
the closest work to OmniFlow in intent: one workflow definition, independent of any provider. Its
binding, however, is the manual one this dissertation removes. Each function in the workflow
carries the concrete endpoint it invokes (a Lambda ARN, a function URL) as a \texttt{resource}
property, and every function must have been deployed beforehand. The workflow is then executed by
xAFCL itself, running as middleware, rather than by AWS Step Functions or Google Cloud Workflows.

\textbf{Serverless Workflow}~\cite{serverlessWorkflowSpec} aims for a vendor-neutral specification for describing workflows and \textbf{Synapse}~\cite{serverlessworkflowSynapse} is an example runtime aligned with that ecosystem. This direction is close to OmniFlow's concern with workflow definition portability but it typically follows a model where workflows are executed by a dedicated runtime rather than translated into a provider-native managed workflow service.

\textbf{Temporal}~\cite{temporalPlatform} is an open-source platform for executing workflows with a \textit{workflows-as-code} approach, using a dedicated cluster and worker processes. It provides execution guarantees such as retries and failure handling, at the cost of introducing an additional runtime layer that must be operated and integrated with cloud services.

\textbf{FaaSr}~\cite{park2024faasr} targets event-driven scientific workflows, with a particular focus on R-based functions. It supports composing functions into workflow graphs (DAGs) and coordinates execution using object storage primitives rather than relying on an always-on workflow engine server. Workflows thus run without a dedicated orchestrator to operate. However, it follows a different strategy from OmniFlow: instead of compiling a workflow DSL into a provider-native workflow resource, it introduces a middleware coordination model focused on scientific workflows and storage-based coordination.

Finally, \textbf{Serverless Multicloud}~\cite{zhao2022supporting} proposes an architecture with a library that abstracts access to serverless offerings across vendors and an evaluation component to analyse cost and performance. This work shares the motivation of reducing vendor lock-in but it emphasises API abstractions and SDK-like interfaces rather than a workflow DSL translation model.

\subsection{Service Registries}

The Function Registry is, in essence, a registry that maps a logical name to an endpoint, and
that problem has established solutions outside serverless workflows. \textbf{AWS Cloud Map} maps
logical names to the resources an application depends on, which register themselves as service
instances, and returns their location through an API call or a DNS query, optionally only for
instances that pass a health check~\cite{awsCloudMap}. \textbf{Consul} keeps a service catalog in
the same role, likewise with health checks and DNS lookup~\cite{consulServiceDiscovery}.

Both differ from the Function Registry in when and by whom the name is resolved. A service registry
is consulted at run time, by the caller, on every lookup. The Function Registry is consulted once,
at deployment time, and its result is written into the workflow definition, so neither the
workflow engine nor the function needs to know that a registry exists. A service registry also
holds only what is registered with it, and deploys nothing, whereas the resolution ladder falls
back to searching the provider and, when the function is absent, to deploying it. Conversely, a
service registry is shared and kept current as instances come and go, which the Function Registry,
a local file validated on each deployment, is not (Section~\ref{sec:concl-critical}).

\subsection{Positioning of This Work}

Table~\ref{tab:related-comparison} summarises the surveyed families against six dimensions that
matter for this thesis. The \emph{Discov.}\ column records whether a function deployed by other
means can be bound by name alone. Three observations stand out. First, the columns are rarely
satisfied together: tooling that automates deployment (IaC) does not address workflow-definition
portability, while tools that target workflow portability (Serverless Workflow, Temporal,
Triggerflow, xAFCL) typically execute the workflow on their own runtime instead of a
provider-native service. Second, deployment-time binding is not new in itself: the IaC tools
already write a function's endpoint into the workflow when both are deployed. Third, mapping
logical names to endpoints is not new either: service registries do it, at run time. What no
surveyed work combines is deployment-time binding with a workflow definition deployable to more
than one provider-native service, with functions written against a provider-agnostic model and,
when a function is missing, with its deployment on demand. The table also marks the limits of
this work: its workflow portability covers two providers, and its discovery is confined to one
account or project, with no shared registry.
