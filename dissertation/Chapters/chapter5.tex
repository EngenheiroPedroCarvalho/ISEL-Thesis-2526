\chapter{Implementation}
\label{cha:impl}

This chapter describes how the architecture and resolution ladder introduced in
Chapter~\ref{ch:proposed_solution} are realised in code.

The chapter is organised in three sections. Section~\ref{sec:function-registry} presents the
Function Registry and the two provider resolvers that consult it at deployment time: how entries
are created and kept up to date, how calls are resolved, and the errors the resolvers raise.
Section~\ref{sec:function-deployment} covers Level~3 of the ladder, the deployment of a missing
function: the change to QuickFaaS's GCP provider that lets the resolvers cover the functions it
deploys, and the AWS Lambda support added to QuickFaaS and OmniFlow.
Section~\ref{sec:runtime-invocation} closes the chapter by following a resolved internal call
through to its actual invocation once the workflow has been deployed.

\section{Function Registry and Resolvers}
\label{sec:function-registry}

Figure~\ref{fig:omniflow-integration-classes} details the classes that realise the unification inside OmniFlow. Function deployment is abstracted behind the \texttt{InternalFunctionDeployer} interface, following the strategy pattern, with three implementations: \texttt{Noop\allowbreak Internal\allowbreak Function\allowbreak Deployer} (the safe default, which raises if invoked), \texttt{QuickFaasDeployer} (GCP), and \texttt{AwsLambdaDeployer} (AWS). Each provider deployer (\texttt{Google\allowbreak Cloud\allowbreak Deployer}, \texttt{Amazon\allowbreak Cloud\allowbreak Deployer}) owns a provider-specific resolver, and both resolvers share two collaborators: the \texttt{Function\allowbreak Registry\allowbreak Store} and the deployer strategy. The store persists each binding as a \texttt{Function\allowbreak Invocation\allowbreak Metadata} record, in the file format of Listing~\ref{lst:registry-structure}. The \texttt{Function\allowbreak Registry\allowbreak Bootstrapper} populates a missing registry by discovery. This structure keeps the two providers symmetric and makes the deployer the extension point: supporting a further platform means adding one resolver and one \texttt{InternalFunctionDeployer}, without touching the existing ones.
\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{images/implementation/omniflow-integration-classes.png}
  \caption{Class model of the integration layer added to OmniFlow.}
  \label{fig:omniflow-integration-classes}
\end{figure}

The registry realises the indirection defined in Section~\ref{sec:dsl-extensions}, through which a
workflow names an internal function by its \texttt{functionRef}, and is also the persistence layer
of the resolution ladder, which creates and refreshes its entries (Section~\ref{subsec:registry-updates}).

\subsection{Creation, Bootstrap and Updates}
\label{subsec:registry-updates}
The registry management layer provides the following behaviour:

\begin{itemize}
    \item \textbf{Bootstrap by discovery:} if the registry file does not exist when a workflow with
    internal calls is deployed, it is created automatically by listing the functions already
    deployed on the target provider (Cloud Run services on GCP, Lambda functions on AWS) and
    writing one entry per discovered function. The
    \texttt{Function\allowbreak Registry\allowbreak Bootstrapper} obtains that listing through
    the \texttt{Cloud\allowbreak Functions\allowbreak Catalog} interface, implemented by
    \texttt{Cloud\allowbreak Run\allowbreak V2\allowbreak Rest\allowbreak Catalog} (GCP) and
    \texttt{Lambda\allowbreak Functions\allowbreak Catalog} (AWS). On
AWS this scans every region enabled for the account. Unlike the ladder, the bootstrap skips a
region it cannot list, with a warning, and fails only when no region can be listed: the registry
is an index that later resolutions validate, so an incomplete one is not unsafe.
    \item \textbf{Automatic registration:} when an internal function is not present in the
    registry but is found on the target provider (Cloud Run service on GCP, Lambda function
    on AWS), a new entry is written immediately with the discovered metadata.
    \item \textbf{Post-deployment updates:} after a successful QuickFaaS deployment, the
    resulting invocation metadata is written to the registry, so subsequent deployments
    resolve the function without redeploying it.
    \item \textbf{Drift handling:} a registry hit whose endpoint has changed is refreshed, and a
    stale entry is replaced or removed as Level~1 of the ladder prescribes
    (Section~\ref{sec:resolution-cascade}).
\end{itemize}

Every write refreshes the top-level \texttt{updatedAt} timestamp.

\subsection{Deployment-Time Endpoint Resolution}
\label{subsec:endpoint-resolution}
The registry is consumed at deployment time by an endpoint resolution step that runs before the
provider-specific artifact (e.g., Google Workflows YAML) is rendered. OmniFlow traverses the
workflow tree (including nested branches, iterations and parallel blocks) and intercepts
every \texttt{CallContext} carrying an \texttt{internalFunction} declaration, leaving external
calls untouched. Each intercepted call is then put through the three-level ladder defined in
Section~\ref{sec:resolution-cascade}. Section~\ref{subsec:store-internals} describes how the two
resolvers realise it, and Section~\ref{subsec:validation-error-semantics} the errors they raise
when a call cannot be bound.

The resolved URL is finally split into \texttt{host} and \texttt{path} (on AWS, into a
\texttt{lambda://<arn>} reference consumed by the renderer) and injected into the call step
before the provider-specific workflow artifact is rendered.
\subsection{Registry Store and Resolver Internals}
\label{subsec:store-internals}

The registry file is manipulated exclusively through \texttt{FunctionRegistryStore}, which
exposes a small interface:
\begin{itemize}
  \item \texttt{readAll()} parses the whole file into an ordered map of \texttt{functionRef} to
  \texttt{Function\allowbreak Invocation\allowbreak Metadata};
  \item \texttt{tryResolveEntry()} re-reads the file via \texttt{readAll()} and delegates the lookup
  to its pure counterpart, \texttt{tryResolveEntryIn()}. The lookup has two steps: an exact match
  on \texttt{functionRef}, then a suffix match on \texttt{"region/\allowbreak functionRef"}, which
  raises an error if it is ambiguous. \texttt{tryResolveEntryIn()} performs it against an
  already-loaded map, with no I/O of its own (\texttt{resolveUrl()} and \texttt{resolveUrlIn()}
  are split in the same way);
  \item \texttt{put()} inserts or refreshes one entry, and \texttt{remove()} deletes a stale one.
\end{itemize}
The store keeps no in-memory state between calls, so \texttt{readAll()} and
\texttt{tryResolveEntry()} re-read and re-parse the file on every call. Chapter~\ref{cha:evaluation}
analyses the performance consequences of this choice.

The two provider resolvers sit on top of this store.
\texttt{WorkflowInternalFunctionResolver} (GCP) realises the three levels of the ladder on the
Cloud Run API, through
\texttt{Cloud\allowbreak Run\allowbreak V2\allowbreak Service\allowbreak Inspector}. The inspector
looks a service up by its full name to validate a hit, and by project, region and name during
discovery.
\texttt{Aws\allowbreak Internal\allowbreak Function\allowbreak Resolver} follows the same shape on the
Lambda API. It reads the region to validate from the stored ARN, and consults the Lambda API
through the \texttt{Lambda\allowbreak Function\allowbreak Inspector} interface.

Region discovery is itself provider-specific. GCP already exposed a project-scoped locations API,
queried through
\texttt{Cloud\allowbreak Run\allowbreak Locations\allowbreak V1\allowbreak Rest\allowbreak Client}.
AWS has no equivalent for Lambda, so a dedicated
\texttt{Aws\allowbreak Regions\allowbreak Lister} interface was added to play that role, implemented
by \texttt{Ec2Aws\allowbreak Regions\allowbreak Lister} on the EC2 \texttt{DescribeRegions} call. The
workflow's own region, when known, is tried first, both when a stale entry is rediscovered and
when a registry miss is searched for. How both resolvers treat a lookup the provider refuses is described in
Section~\ref{subsec:validation-error-semantics}.

In both resolvers, the writes listed in Section~\ref{subsec:registry-updates} go through
\texttt{put()} before the endpoint is injected into the call, and a hit that validates unchanged
writes nothing. The registry therefore converges toward a complete set of bindings as workflows
are deployed. The sequence diagrams of Appendix~\ref{app:cascade-sequences}
(Figures~\ref{fig:resolution-cascade-level1}--\ref{fig:resolution-cascade-level3}) show, level by
level and with GCP and AWS side by side, the messages each resolver exchanges with the registry
and with its provider's inspection API.

To keep resolution cheap when a workflow contains many internal calls, both provider resolvers
read the registry once into a snapshot at the start of \texttt{resolve()}, and resolve every call
against that in-memory map instead of re-reading the file per call. The snapshot is kept in sync
with every subsequent \texttt{put()} and \texttt{remove()}, so two calls to the same function
within one workflow still observe each other's writes.

\subsection{Validation and Error Semantics}
\label{subsec:validation-error-semantics}
The failure modes of the ladder are listed in Section~\ref{sec:walkthrough}. Two details belong
here. Supplying a \texttt{deploymentDescriptorPath} does not resolve an ambiguous reference, because
ambiguity is a data-consistency problem rather than an absence, so QuickFaaS is never invoked to
hide it. And a lookup the provider refuses is treated as follows.

\paragraph{Insufficient permissions.}
If the live lookup used to validate a registry hit is refused (an authorisation failure rather
than an absence), deployment aborts immediately with a diagnostic naming the function. On GCP, no
rediscovery is attempted, since a permissions failure gives no information about whether the
service still exists. The same rule applies on AWS, where a refused \texttt{GetFunction} is
likewise distinguished from a genuine absence. The distinction is drawn more coarsely when a
registry miss is searched for across regions, on both providers. While the scan is running, a region where the lookup is
refused is simply excluded from the candidate set, the same as a region where the function is
absent, so a permissions gap in one region does not by itself stop a match found elsewhere. If the
scan ends with no match anywhere and at least one region could not be checked, however, it reports
a diagnostic naming the inaccessible regions instead of silently concluding that the function is
absent everywhere.

\subsection{Evolution of the Registry Design}
\label{subsec:registry-evolution}

The registry did not arrive at its current form in a single step. Its starting point was
the indirection of Section~\ref{sec:dsl-extensions}. Three threads describe how it evolved from there.

\paragraph{From provider-specific fields to a uniform endpoint.}
Collapsing the endpoint into one \texttt{url} field is what let the AWS extension reuse the
registry unchanged. Because \texttt{url} is treated as an opaque, provider-interpreted string (an HTTPS
endpoint on GCP, a Lambda ARN on AWS), the registry schema did not have to change when the AWS
provider was added: only the resolver that reads the field and the renderer that consumes it are
provider-aware. The registry format is thus the same on both providers.

\paragraph{From a manually edited file to an auto-managed source of truth.}
The registry also evolved from something the developer would maintain by hand into something the
integration maintains automatically, through the bootstrap, registration, refresh and pruning
listed in Section~\ref{subsec:registry-updates}. In parallel, the single-read snapshot of Section~\ref{subsec:store-internals}
replaced re-reading the file on every lookup, first in a reference resolver used by the
benchmarks and then in the two production resolvers. Chapter~\ref{cha:evaluation} quantifies the
effect on both.

\paragraph{From a trusted cache to a verified indirection.}
The two production resolvers did not always treat a registry hit the same way.
\texttt{Workflow\allowbreak Internal\allowbreak Function\allowbreak Resolver} (GCP) validated every hit against the live
Cloud Run service from the start, because a Cloud Run lookup needs the project/region/service
triple that only the registry supplies. The one exception, first-generation Cloud Functions, which
it returned unchecked, disappeared when QuickFaaS moved to second-generation functions
(Section~\ref{subsec:gcp-cloud-run-functions}). \texttt{Aws\allowbreak Internal\allowbreak Function\allowbreak Resolver} initially
trusted a hit outright, returning the cached ARN with no live check, since a Lambda name is
already unique within a region and validating brought no discovery benefit on its own. This
asymmetry was closed by introducing \texttt{Lambda\allowbreak Function\allowbreak Inspector}, the AWS counterpart to
the Cloud Run inspector: a hit is now confirmed live on both providers
(Section~\ref{subsec:store-internals}). The change did not make the registry
redundant, only its trust model stricter: the live check answers whether a binding the registry
already named is still accurate, not what to look up or whether a deployment is needed.

\section{Function Deployment at Level~3}
\label{sec:function-deployment}
When the ladder reaches Level~3, the resolver hands the call to the provider's
\texttt{Internal\allowbreak Function\allowbreak Deployer}, which runs QuickFaaS as a subprocess
(Section~\ref{sec:design-rationale}) and returns the registry entry of the new function. On GCP
this required moving QuickFaaS to second-generation functions
(Section~\ref{subsec:gcp-cloud-run-functions}). On AWS it required a new QuickFaaS provider and a
deployer that prepares the IAM role and permissions around it
(Sections~\ref{subsec:aws-lambda-deployment}--\ref{subsec:omniflow-aws-deployer}).

\subsection{Cloud Run Functions on GCP}
\label{subsec:gcp-cloud-run-functions}
The GCP resolver validates and discovers functions only through the Cloud Run API, so the functions
the integration deploys on GCP must be Cloud Run services. The original QuickFaaS deploys
first-generation Cloud Functions (Section~\ref{sec:background_quickfaas}), which are not. Its GCP
provider was therefore moved to the Cloud Functions~v2 API, which creates \emph{Cloud Run
functions}: functions backed by a Cloud Run service~\cite{gcpFunctionsVersionComparison}. Only
the HTTP trigger, the one internal calls use, was exercised on GCP.

The v2 deployment is a long-running operation, and the backing service exists only once the build
has finished. QuickFaaS therefore waits until the function reports the \texttt{ACTIVE} state and
only then reads its URL and opens it to invocation. The URL cannot be composed from the project,
region and name, as a first-generation \texttt{cloudfunctions.net} URL could: the
\texttt{run.app} host carries a hash generated by Google, and the API returns it as
\texttt{serviceConfig.uri}. Invocation permission is granted on the backing Cloud Run service,
named in \texttt{serviceConfig.service}, since that is where Cloud Run enforces it: QuickFaaS grants
\texttt{roles/\allowbreak run.invoker} to all users, as its first-generation provider did with
the Cloud Functions invoker role. On the OmniFlow side, \texttt{QuickFaasDeployer} waits
for the same state and, when it is given the service account the workflow runs as, grants that
account \texttt{roles/\allowbreak run.invoker} on the service (a failed grant is reported with the
equivalent \texttt{gcloud} command, and does not stop the deployment). It then returns the two fields of the registry entry: the URL, and,
as its \texttt{serviceName}, the full resource name of the service, which is the form the
inspector looks up at Level~1.

All three levels of the ladder and the registry bootstrap therefore cover these functions through
the Cloud Run clients described above, and only the Level~3 deployment itself calls the Cloud Functions
API. The resolver validates every registry hit: the URL does not
identify the generation of the function behind it, since a second-generation function keeps a
\texttt{cloudfunctions.net} endpoint besides its \texttt{run.app}
one~\cite{gcpFunctionsVersionComparison}. First-generation functions created outside the
integration are not supported: neither discovery nor the bootstrap lists them, and a registry entry
that points to one fails validation like a deleted service.

\subsection{Deployment on AWS}
\label{subsec:aws-lambda-deployment}
Figure~\ref{fig:aws-deploy-sequence} traces the end-to-end deployment on AWS, from the registry bootstrap to \texttt{Create\allowbreak State\allowbreak Machine}, and expands the longest path, where an internal function exists in neither the registry nor AWS. The \texttt{alt} fragment (UML notation for alternative branches) has one branch for each of the three levels of the resolution ladder described in Section~\ref{sec:resolution-cascade}, and a fourth for the calls that fail fast. Once Level~3 is reached, \texttt{AwsLambdaDeployer} performs the AWS-specific work described step by step in Section~\ref{subsec:omniflow-aws-deployer}. The ARN it returns is stored in the registry and, once all calls are resolved, the workflow is rendered with a \texttt{lambda:invoke} task resource and submitted via \texttt{Create\allowbreak State\allowbreak Machine}.

AWS support is realised in two layers that meet at the subprocess boundary: the AWS provider added
\emph{inside} QuickFaaS, which performs the actual Lambda deployment, and the
\texttt{Aws\allowbreak Lambda\allowbreak Deployer} added \emph{inside} OmniFlow, which prepares the environment,
drives QuickFaaS, and produces the invocation metadata the registry stores.

\subsection{The QuickFaaS AWS Provider}
\label{subsec:quickfaas-aws-provider}

The AWS provider extends QuickFaaS's existing abstractions (\texttt{CloudProvider},
\texttt{Cloud\allowbreak Function}, \texttt{CloudRequests}) so that a cloud-agnostic function can be packaged
and deployed to AWS Lambda through the same ZIP strategy used for GCP and Azure. Its core is
\texttt{AwsLambdaFunction.deployZip}. It uploads the packaged archive to the S3 bucket named in
the descriptor and checks whether the function already exists (\texttt{GetFunction}). It then
either creates the function (\texttt{CreateFunction}, with the code referenced as an S3 object) or
updates its code (\texttt{UpdateFunctionCode}), and in both cases blocks on the AWS SDK waiter
until the function is active. The handler is fixed to the provider-agnostic entry point \texttt{AwsHttpTemplate}, which
adapts the Lambda request to the developer's hook, and the supported runtimes are \texttt{java11}
and \texttt{java17}. To place the function in its code bucket's region
(Section~\ref{sec:resolution-cascade}), the provider reads that region with \texttt{GetBucketLocation},
issued against the global endpoint in \texttt{us-east-1}, and pins the Lambda client to it. Finally, the
provider creates (or reuses) a Lambda \emph{Function URL} with \texttt{AuthType = AWS\_IAM},
QuickFaaS's own notion of an invocation endpoint.

\subsection{The OmniFlow-Side AWS Deployer}
\label{subsec:omniflow-aws-deployer}

\texttt{AwsLambdaDeployer} is the AWS implementation of the \texttt{InternalFunctionDeployer}
strategy. It performs the work that has no GCP equivalent and that must happen \emph{around} the
QuickFaaS subprocess. From the raw descriptor it resolves or creates the Lambda execution IAM
role. If \texttt{iamRoleArn} is blank or a placeholder, it creates a managed
\texttt{OmniFlowLambdaExecutionRole} (attaching \texttt{AWSLambdaBasicExecutionRole}). If a real
ARN is supplied, it verifies the role's trust policy and, if necessary, repairs it so that
\texttt{lambda.amazonaws.com} can assume the role. The resolved ARN is patched into a temporary copy of
the descriptor, the effective region is taken from the S3 bucket's location, and QuickFaaS is
invoked as a subprocess. If Lambda reports that it cannot yet assume a newly created role, the
invocation is repeated after 20 seconds, up to three attempts in all, to absorb IAM eventual
consistency. After the subprocess returns, the deployer polls \texttt{GetFunction} until
the function reports the \texttt{Active} state (bounded by a 180-second timeout), retrieves the ARN,
and grants the Step Functions service principal permission to invoke the function.

Although the QuickFaaS provider produces a Function URL,
the OmniFlow deployer discards it and stores the \emph{ARN} in the registry, because internal calls
are rendered with the native \texttt{lambda:invoke} integration (Section~\ref{sec:runtime-invocation})
rather than as HTTP calls to a Function URL. Listing~\ref{lst:aws-descriptor} shows a minimal AWS
deployment descriptor. It has the fields of the GCP descriptor of
Listing~\ref{lst:quickfaas_json_config}, with AWS values: \texttt{cloudProvider} is
\texttt{"aws"}, \texttt{project} the account number, \texttt{location} an AWS region and
\texttt{bucket} an S3 bucket, while \texttt{accessToken} is left empty, because the AWS provider
takes its credentials from the environment. It adds one field, \texttt{iamRoleArn}, which may be left as a
placeholder to request automatic role creation.

\begin{lstlisting}[language=json,caption={Minimal AWS deployment descriptor for an internal function.},label={lst:aws-descriptor}]
{
  "cloudProvider": "aws",
  "accessToken": "",
  "project": "123456789012",
  "iamRoleArn": "<auto>",
  "function": {
    "name": "hello-lambda-fn",
    "location": "eu-west-1",
    "bucket": "run-sources-tfm2526-eu-west-1",
    "runtime": "java17",
    "trigger": { "type": "http" }
  },
  "functionFile": "./MyFunctionClass.java"
}
\end{lstlisting}

\section{Runtime Invocation}
\label{sec:runtime-invocation}
Figure~\ref{fig:aws-runtime-invocation} shows how an internal function is invoked at runtime, once the workflow is deployed. Step Functions invokes the Lambda directly, through the native \texttt{arn:aws:states:::lambda:invoke} integration and with the ARN fixed at deployment time. The QuickFaaS template entry point, \texttt{AwsHttpTemplate}, reads only the \texttt{queryStringParameters} of the event it receives, and passes them to the developer's hook function as a map. The response is returned under \texttt{\$.Payload}. An internal call on AWS therefore passes its inputs with \texttt{query(\ldots)}. A call that declares a body is rejected by \texttt{Aws\allowbreak Internal\allowbreak Function\allowbreak Resolver} before the ladder runs, rather than rendered into a state machine that would silently drop it. Using the native integration rather than an HTTP endpoint avoids per-call request signing and keeps the invocation within the AWS control plane.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.8\textwidth]{images/implementation/aws-runtime-invocation.png}
  \caption{Runtime invocation of an internal function on AWS via the native
  \texttt{lambda:invoke} integration.}
  \label{fig:aws-runtime-invocation}
\end{figure}


Internal and external calls are told apart entirely by the renderer,
\texttt{AmazonCall\allowbreak Renderer}, from the \texttt{host} value injected during resolution. If the host
carries the \texttt{lambda://} prefix (the marker written by \texttt{Aws\allowbreak Internal\allowbreak Function\allowbreak Resolver}),
the renderer emits a \texttt{Task} whose \texttt{Resource} is
\texttt{arn:aws:states:::lambda:invoke} and whose \texttt{Parameters} carry the
\texttt{FunctionName} taken from the resolved ARN. Any query terms are forwarded under a
\texttt{Payload.queryStringParameters} object. Otherwise it emits the original
\texttt{apigateway:invoke} task with \texttt{ApiEndpoint}, \texttt{Method} and \texttt{Path}. For
the Lambda form the result is extracted with a \texttt{ResultSelector} that reads
\texttt{\$.Payload} into the step's result variable, and the value is scoped under a
\texttt{ResultPath} named after the step so that later steps can reference it. Listing
\ref{lst:rendered-lambda} shows the state a \texttt{call} to \texttt{internalFunction("fraud-check")}
renders to. Its \texttt{InputPath} passes the whole state document to the task, and \texttt{Next}
names the state that follows, as for any other step.

\begin{lstlisting}[language=json,caption={Step Functions state rendered for an internal Lambda call.},label={lst:rendered-lambda}]
"fraud-check": {
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke",
  "InputPath": "$",
  "Parameters": {
    "FunctionName": "arn:aws:lambda:eu-west-1:123456789012:function:fraud-check"
  },
  "ResultSelector": { "fraudResult.$": "$.Payload" },
  "ResultPath": "$.fraud-check",
  "Next": "external-risk-api"
}
\end{lstlisting}

Keeping the internal form as a variant of the existing \texttt{call} renderer (rather than a new
state type) means the control-flow, result-passing and error-handling machinery that OmniFlow
already emits for external calls applies unchanged to internal ones: only the \texttt{Resource} and
the parameter shape differ.

On GCP, an internal call needs no renderer of its own. The resolver has already split the
\texttt{run.app} URL into \texttt{host} and \texttt{path}, so \texttt{GoogleCallRenderer} emits the
same step it emits for an external call: a \texttt{call: http.post} (or the verb the step
declares) whose \texttt{args.url} is the resolved URL. Authentication is not added by the
resolver. It is declared on the call step, as for any external call, with
\texttt{authentication(\allowbreak authentication \{ type("OIDC") \})}. The renderer then emits \texttt{auth: type: OIDC}, and
Cloud Workflows attaches to each request an identity token for the service account the workflow
runs as. That is the account to which \texttt{QuickFaasDeployer} grants
\texttt{roles/\allowbreak run.invoker} (Section~\ref{subsec:gcp-cloud-run-functions}). QuickFaaS,
however, also grants that role to all users, so a function it deploys accepts unauthenticated
requests as well. While that grant stands, the OIDC token and the grant to the workflow's service
account are redundant, and become the access control only once the public grant is removed.
