\chapter{Conclusions and Future Work}
\label{cha:conclusions}

This dissertation set out to unify two previously independent tools (QuickFaaS, which deploys
serverless functions, and OmniFlow, which defines and deploys workflows) so that a serverless
application can be deployed from a single workflow definition, without manually coordinating
function endpoints. This final chapter summarises the contribution, revisits the objectives,
assesses the work critically, and outlines future directions.

\section{Summary of Contributions}
\label{sec:concl-contributions}

The work delivered two complementary halves: the unification of function and workflow deployment,
through the Function Registry and the deployment-time resolution ladder
(Chapters~\ref{ch:proposed_solution} and~\ref{cha:impl}), and the AWS Lambda provider added to
QuickFaaS, with the matching deployer in OmniFlow (Section~\ref{subsec:quickfaas-aws-provider}).
To let the ladder cover the functions it deploys on GCP, QuickFaaS's GCP provider was also moved
to second-generation functions, which are Cloud Run services
(Section~\ref{subsec:gcp-cloud-run-functions}).
How far each meets the objectives set out in Chapter~\ref{cha:introduction} is assessed next.

\section{Objectives Revisited}
\label{sec:concl-objectives}

The two research questions of Section~\ref{sec:int_objectives} are answered as follows:
\begin{itemize}
  \item \textbf{RQ1 (feasibility and correctness)}: yes, for the resolution logic. On both AWS
  and GCP the ladder binds each internal call to the right endpoint and deploys a function only
  when its absence is confirmed, and it aborts on stale entries, ambiguous names and inaccessible
  regions (Section~\ref{sec:eval-correctness}), within the limits stated below for objective 4.
  \item \textbf{RQ2 (overhead)}: small. In the production resolvers, resolving a workflow of 200
  internal calls against a registry of ten functions takes $29\,\mu$s on AWS and $199\,\mu$s on GCP,
  growing linearly with the number of internal calls, while the registry is read once per
  deployment (Section~\ref{sec:eval-discussion}). On the provider side, resolution sends one
  request per internal call when the registry is current (Section~\ref{sec:eval-api-calls}).
\end{itemize}

Against the four objectives stated in Section~\ref{sec:int_objectives}, the work stands as
follows:
\begin{enumerate}
  \item \textbf{Design a unified integration architecture}: \emph{met.} The registry, the
  \texttt{functionRef} indirection, the \texttt{internalFunction} construct and the resolver
  strategy (Chapters~\ref{ch:proposed_solution} and~\ref{cha:impl}) let a single workflow
  definition drive both function and workflow deployment, binding endpoints when the workflow is
  deployed (Section~\ref{sec:resolution-cascade}).
  \item \textbf{Implement an orchestration prototype}: \emph{met.}
  The prototype resolves the internal functions of a workflow on both providers, and deploys the
  missing ones, without endpoints being copied by hand.
  \item \textbf{Extend QuickFaaS to AWS Lambda}: \emph{met.} QuickFaaS gained an AWS provider
  and OmniFlow an \texttt{AwsLambdaDeployer} (Sections~\ref{subsec:quickfaas-aws-provider}
  and~\ref{subsec:omniflow-aws-deployer}). The provider-agnostic packaging layer adds about
  0.9\,KB to a Lambda bundle (Table~\ref{tab:eval-s1}), and the resolver tests cover both
  providers (Section~\ref{sec:eval-correctness}).
  \item \textbf{Evaluate feasibility and overhead}: \emph{partially met.}
  Chapter~\ref{cha:evaluation} checks the decisions of the resolution ladder on both providers
  and measures the resolution overhead, the registry write path and the packaging size. The
  evidence is mostly local: apart from the GCP deployment of the case study
  (Section~\ref{sec:case-artifacts}), the correctness checks simulate the provider, nothing ran
  against AWS, and the benchmarks ran on a laptop rather than dedicated hardware. End-to-end deployment times were deliberately not
  measured, since they are known to take minutes and are dominated by the provider
  (Section~\ref{sec:eval-scope}). The
  provider calls that validation and discovery make are counted from the code
  (Section~\ref{sec:eval-api-calls}) rather than timed.
\end{enumerate}

\section{Critical Assessment}
\label{sec:concl-critical}

The implementation is that of a prototype, and several limitations should be stated plainly.

\begin{itemize}
  \item \textbf{Static binding.} Endpoints are resolved when the workflow is deployed and embedded
  in the rendered artifact (Section~\ref{sec:resolution-cascade}). An endpoint that changes afterwards
  reaches a deployed workflow only when that workflow is deployed again, since nothing resolves
  endpoints at run time.
  \item \textbf{No update path.} The ladder deploys a function only when it is missing and never
  updates one that exists: a change to a function's code is not deployed by a workflow deployment,
  and has to be deployed separately (for example, with QuickFaaS directly).
  \item \textbf{Workflow redeployment.} OmniFlow's deployers create a workflow and cannot update
  one, so deploying a workflow again means deleting it first (Section~\ref{sec:case-artifacts}). The
  second deployments described in Sections~\ref{sec:walkthrough} and~\ref{sec:case-artifacts}
  assume that step.
  \item \textbf{Bare references and restricted regions.} A bare \texttt{functionRef} that misses
  the registry is looked for in every region, and a region that refuses the lookup stops the
  resolution. In a project where some regions are closed by policy, such references abort, and the
  region-qualified form that avoids the scan ties the definition to one provider's region names
  (Section~\ref{sec:case-discussion}).
  \item \textbf{Unguarded registry.} The registry is a flat JSON file with no cache, no integrity
  or authenticity guarantee, and no cross-process locking: concurrent writers race, and a tampered
  \texttt{url}/ARN would be trusted blindly.
  \item \textbf{A per-machine index, not a shared store.} The registry lives in the working
  directory of whoever deploys. The shared record of the deployed functions is the provider itself:
  every registry hit is validated against it, and a missing registry is rebuilt from it. Two
  developers deploying the same workflow therefore converge on the same bindings, but each through
  their own requests to the provider. They do not share a registry.
  \item \textbf{Cloud Run services only on GCP.} Validation, discovery and the bootstrap see
  only Cloud Run services, so first-generation Cloud Functions created outside the integration
  cannot be bound (Section~\ref{subsec:gcp-cloud-run-functions}).
  \item \textbf{Broad, automatic IAM.} The AWS path auto-creates and mutates a shared execution
  role and grants invoke permissions as a deployment side effect: convenient for a demo, but at
  odds with a least-privilege, change-controlled environment. On GCP, QuickFaaS opens every
  function it deploys to all users, which makes the invoker role granted to the workflow's service
  account redundant (Section~\ref{sec:runtime-invocation}).
  \item \textbf{Brittle integration boundary.} QuickFaaS is invoked as a subprocess, coupling two
  build systems across a process boundary and detecting errors from the subprocess output. The
rationale for this boundary, and the in-process alternative, is discussed in
  Section~\ref{sec:design-rationale}.
  \item \textbf{Testability of cloud paths.} By design, the classes that call the cloud SDKs have
  no automated coverage, so the integration edges (where production incidents occur) are the
  least tested.
\end{itemize}

\section{Future Work}
\label{sec:concl-future}

The following directions are ordered from smallest change with the clearest payoff to the larger
structural ones.

\begin{enumerate}
  \item \textbf{Add an update path:} record a hash of each function's source in its registry entry
  and redeploy the function through QuickFaaS when the source its descriptor points to changes, so
  that a workflow deployment also brings its functions up to date.
  \item \textbf{Harden the registry:} a pluggable, access-controlled backend (database or secret/parameter store)
  behind the current interface, with cross-process locking, per-entry integrity, an in-memory
  cache with explicit invalidation, and an append-only, attributable write history.
  \item \textbf{Replace the subprocess boundary} by invoking QuickFaaS in-process as a library
  (Section~\ref{sec:design-rationale}).
  \item \textbf{Move to least-privilege, change-controlled IAM,} with pre-provisioned roles and a
  dry-run mode that reports the IAM changes it would make instead of applying them silently.
  \item \textbf{Make the cloud-calling code testable,} extracting the SDK interactions
  behind narrow interfaces so the deploy/IAM/readiness logic can be unit-tested against fakes.
  \item \textbf{Validate the ladder against live providers,} on AWS, and on GCP beyond the single
  workflow of Chapter~\ref{cha:case-study}, deploying workflows that contain internal calls at each
  level of the ladder, so that the correctness
  evidence of Section~\ref{sec:eval-correctness} rests on the providers' own responses rather than
  on test doubles.
  \item \textbf{Extend the provider set,} adding Azure Functions (already a QuickFaaS target)
  through the existing extension point to further substantiate the portability claim.
\end{enumerate}

\section{Final Remarks}
\label{sec:concl-final}

The integration shows that function deployment and workflow orchestration can be driven from a
single, provider-agnostic definition, with concrete endpoint binding deferred to deployment time
through an explicit resolution ladder. In local measurements the overhead of this unification is
small and, with the single-read optimisation applied in both production resolvers, grows linearly.
The solution fits an organisation that deploys one orchestration to several accounts or providers,
as the case study of Chapter~\ref{cha:case-study} illustrates, or that exposes open-banking
functions under PSD2. What remains is evidence against AWS and engineering maturity (registry
integrity, least-privilege operation, test coverage of the cloud edges and an update path) to
take the prototype to production.
