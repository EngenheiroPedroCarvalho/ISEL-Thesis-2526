\chapter{Conclusions and Future Work}
\label{cha:conclusions}

This dissertation unified QuickFaaS, which deploys serverless functions, and OmniFlow, which
defines and deploys workflows, so that a serverless application is deployed from a single workflow
definition, without function endpoints being coordinated by hand.

\section{Summary of Contributions}
\label{sec:concl-contributions}

The work delivered the five contributions of Section~\ref{sec:int_contributions}. The first is the
\texttt{internalFunction} construct, which separates internal from external calls
(Section~\ref{sec:dsl-extensions}). The second, the core of the unification, is a per-provider
Function Registry and a three-level resolution sequence that binds each internal call at deployment
time (Sections~\ref{sec:resolution-cascade} and~\ref{sec:function-registry}). The third extends the
sequence's reach: an AWS Lambda provider in QuickFaaS, with the matching OmniFlow deployer, and the
move of QuickFaaS's GCP provider to second-generation functions, so that the sequence covers the
functions it deploys (Section~\ref{sec:function-deployment}). The last two put the result to the
test: a prototype and a case study of a payment authorization workflow, run on AWS and GCP
(Chapter~\ref{cha:case-study}), and an evaluation of the sequence's decisions and of the cost of
resolution (Chapter~\ref{cha:evaluation}).

\section{Objectives Revisited}
\label{sec:concl-objectives}

The first research question, on feasibility and correctness, is answered positively for the
resolution logic. On both providers the sequence binds each internal call to the right endpoint,
deploys a function only when its absence is confirmed, and aborts on stale entries, ambiguous names
and inaccessible regions (Section~\ref{sec:eval-correctness}), with the limits stated below for the
fourth objective. The answer to the second, on overhead, is that it is small. The production
resolvers resolve 200 internal calls against a registry of ten functions in $29\,\mu$s on AWS and
$199\,\mu$s on GCP, and the time grows linearly with the number of internal calls, with one registry
read per deployment (Section~\ref{sec:eval-discussion}). When the registry is current, resolution
sends one provider request per internal call (Section~\ref{sec:eval-api-calls}).

Of the objectives of Section~\ref{sec:int_objectives}, the first three were met and the fourth only
in part. The unified integration architecture is the registry, the \texttt{functionRef}, the
\texttt{internalFunction} construct and the resolver strategy, which together let one definition
drive both deployments (Chapters~\ref{ch:proposed_solution} and~\ref{cha:impl}). The orchestration
prototype resolves a workflow's internal functions on both providers, and deploys the missing ones,
without endpoints being copied by hand. QuickFaaS was extended to AWS Lambda with a new provider,
and OmniFlow with an \texttt{AwsLambdaDeployer} (Section~\ref{subsec:aws-lambda-deployment}); the
provider-agnostic layer adds about 0.9\,KB to a Lambda bundle (Table~\ref{tab:eval-s1}). The
evaluation of feasibility and overhead is the objective met only in part. Apart from the case
study's deployments (Section~\ref{sec:case-artifacts}), the correctness checks simulate the
provider, and the benchmarks ran on a laptop. End-to-end deployment times were not measured, since
the provider dominates them (Section~\ref{sec:eval-scope}), and provider requests were counted from
the code, not timed (Section~\ref{sec:eval-api-calls}).

\section{Critical Assessment}
\label{sec:concl-critical}

The implementation is a prototype, and its limitations fall into four groups.

The first is the life cycle of what is deployed. Binding is static: an endpoint that changes after
deployment reaches the workflow only when the workflow is deployed again
(Section~\ref{sec:resolution-cascade}). The sequence deploys only missing functions, so a code change
must be deployed separately, for example with QuickFaaS directly. And OmniFlow's deployers cannot
update a workflow, which must be deleted before being deployed again
(Section~\ref{sec:case-artifacts}).

The second is portability, which the definition reaches only in part. A bare reference that misses
the registry is searched for in every region. If some regions refuse the lookup and the function is
found nowhere, the resolution aborts instead of reaching Level~3, and the region-qualified form that
avoids the scan ties the definition to one provider's region names. The AWS renderer turns a
multi-variable \texttt{assign} into a \texttt{Pass} state that replaces the whole state, and the two
renderers expect a literal host in different forms, so external calls are not portable. QuickFaaS's
GCP hook and AWS template use different signatures, so each internal function is written once per
provider (Section~\ref{sec:case-discussion}). On GCP, only Cloud Run services can be bound:
first-generation Cloud Functions created outside the integration cannot
(Section~\ref{subsec:gcp-cloud-run-functions}).

The third is the registry. It is a flat JSON file with no cache, no integrity guarantee and no
cross-process locking: concurrent writers race, and a tampered \texttt{serviceName} that names
another existing function would be accepted (a tampered \texttt{url} is corrected by validation).
It is also a per-machine index, not a shared store. Each developer has their own registry; the
shared record is the provider itself, against which every hit is validated and from which a missing
registry is rebuilt, so developers converge on the same bindings, each through their own requests.

The fourth is operation. IAM changes are broad and automatic: on AWS, a shared execution role is
created or modified and invoke permissions are granted as side effects; on GCP, QuickFaaS opens
every function to all users, making the grant to the workflow's service account redundant
(Section~\ref{subsec:gcp-cloud-run-functions}). Neither suits a least-privilege environment. The
integration between the two tools is loose: OmniFlow runs QuickFaaS as a separate process rather
than calling it as a library, and parses its output (Section~\ref{sec:design-rationale}). And, by design, the classes that call cloud SDKs have no
automated tests, so the integration edges are the least tested part of the code.

\section{Future Work}
\label{sec:concl-future}

From the smallest change with the clearest payoff to the larger ones:

\begin{enumerate}
  \item \textbf{Add an update path:} store a hash of each function's source in its registry entry
  and redeploy the function when the source changes.
  \item \textbf{Harden the registry:} an access-controlled backend (database or parameter store)
  behind the current interface, with locking, per-entry integrity, caching and an attributable
  write history.
  \item \textbf{Invoke QuickFaaS in-process} as a library instead of a subprocess
  (Section~\ref{sec:design-rationale}).
  \item \textbf{Least-privilege IAM:} pre-provisioned roles and a dry-run mode that reports IAM
  changes instead of applying them.
  \item \textbf{Testable cloud code:} SDK interactions behind narrow interfaces, so the deployment,
  IAM and readiness logic can be tested against fakes.
  \item \textbf{Validate the sequence on live providers} at every level, beyond the single workflow of
  Chapter~\ref{cha:case-study}, so that the evidence of Section~\ref{sec:eval-correctness} rests on
  the providers' own responses.
  \item \textbf{Add Azure Functions}, already a QuickFaaS target, through the existing extension
  point.
\end{enumerate}

\section{Final Remarks}
\label{sec:concl-final}

Function deployment and workflow orchestration can be driven from a single, provider-agnostic
definition, with endpoints bound at deployment time by an explicit resolution sequence. The local
overhead is small and, with the single registry read, grows linearly.

Without the integration, a developer deploys each function with QuickFaaS, copies its endpoint into
the workflow and then deploys the workflow with OmniFlow, keeping the two in step by hand. With it,
the workflow names its internal functions, and one deployment finds or deploys each of them and
writes its endpoint into the workflow. With the AWS provider, QuickFaaS deploys to both providers
OmniFlow renders for, so the same definition can be deployed, with its functions, to either one,
although each function's source is still written per provider.

Two design decisions shaped the result. The tools stay separate: OmniFlow drives QuickFaaS as an
external process, through one deployer per provider, so each keeps its own build and toolchain, and
another provider means one more deployer and resolver. And the sequence is conservative: it deploys a
function only when its absence is confirmed and aborts on anything uncertain, preferring a failed
deployment to a workflow bound to the wrong function. Most of the limitations above call for
engineering work rather than new design.

The approach suits an organisation that deploys one workflow to several accounts or providers, as
the case study illustrates. Taking it to production requires live evidence beyond one workflow and
engineering maturity: registry integrity, least-privilege operation, tests of the cloud edges and
an update path.
