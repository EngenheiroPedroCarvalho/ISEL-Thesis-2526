%% Abstract in English
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
A serverless workflow is written before the functions it calls exist. Its endpoint --- a Cloud Run URL, a Lambda
ARN --- is produced by its deployment and depends on the account, project, region and provider it
was deployed to. The developer therefore deploys the functions with one tool, reads the endpoints
it produced, and copies them by hand into the workflow definition consumed by another. The copying is repeated whenever a function moves between regions, accounts or
providers, and a mistyped endpoint yields a workflow that deploys successfully and only fails when
it runs.

This dissertation removes that step by unifying the two tools: QuickFaaS, which deploys portable
serverless functions, and OmniFlow, a Kotlin DSL that renders and deploys workflows to AWS Step
Functions and Google Cloud Workflows. A workflow call names a function by a stable logical
identifier rather than by an endpoint, and a three-level resolution cascade binds that identifier
when the workflow is deployed: it reads a per-provider function registry and validates the entry
against the live function; failing that, it searches the provider's regions; and only when absence
is confirmed does it deploy the function through QuickFaaS from a deployment descriptor. QuickFaaS,
previously limited to Google Cloud and Azure, was also extended with an AWS Lambda provider,
covering the same two clouds as OmniFlow.

The prototype is evaluated for correctness and for overhead. Forty-five resolver unit tests cover
every path of the cascade on both providers, and benchmarks show that local resolution costs
milliseconds for workflows of up to two hundred internal calls, growing linearly with the number of
internal calls and not with the size of the registry. Deploying a serverless application from a
single definition is therefore feasible, and the resolution it adds is small beside the cloud
deployment it precedes.
