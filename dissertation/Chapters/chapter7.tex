This chapter answers the research questions of Section~\ref{sec:int_objectives}: whether internal
calls are bound correctly at deployment time on both providers (RQ1), and how much local work that
resolution adds and how many provider requests it sends (RQ2).

\section{Scope and Goals}
\label{sec:eval-scope}

The evaluation covers only \emph{local} operations: building and traversing the workflow model,
resolving internal calls, reading and writing the registry, and packaging a Lambda bundle.
Operations that call the provider (Lambda, IAM, S3, Cloud Run and Cloud Functions requests, the
QuickFaaS subprocess) are excluded: deploying a workflow and its functions takes minutes, with or
without this integration, and is non-deterministic. Each question is answered as follows:

\begin{itemize}
  \item \textbf{RQ1, correct binding on both providers:} resolver unit tests, with the provider
  replaced by test doubles (Section~\ref{sec:eval-correctness}).
  \item \textbf{RQ2, local work added by resolution:} JMH benchmarks of a reference resolver and of
  the production resolvers (Sections~\ref{sec:eval-resolution} and~\ref{sec:eval-real-resolvers}).
  \item \textbf{RQ2, requests sent to the provider:} an analytical count, derived from the code
  path by path through the ladder, since the benchmarks run without a network
  (Section~\ref{sec:eval-api-calls}).
  \item \textbf{Manual steps removed and cost of portability on AWS:} a procedural comparison of
  developer actions, and the Lambda bundle size, provider-agnostic vs.\ native
  (Section~\ref{sec:eval-manual-effort}).
\end{itemize}

\section{Correctness of the Resolution Ladder}
\label{sec:eval-correctness}

Each production resolver (\texttt{Aws\allowbreak Internal\allowbreak Function\allowbreak Resolver}
and \texttt{Workflow\allowbreak Internal\allowbreak Function\allowbreak Resolver}, the classes OmniFlow
runs when it deploys a workflow) has a unit-test suite that resolves a small workflow in each
situation the ladder can meet. The provider is replaced by test doubles (a lookup that answers ``found'', ``not found'' or ``access denied'' per
region, a fixed region list, and a deployer that records what it is asked to deploy). What the tests
verify is therefore the resolver's decision given a simulated provider answer, not the provider
itself. The registry, in contrast, is not replaced by a test double: the tests use the same registry
class that OmniFlow uses when it deploys a workflow (\texttt{Function\allowbreak Registry\allowbreak
Store}), which reads and writes a JSON file in the same format. The file lives in a temporary
directory that the test framework (JUnit's \texttt{@TempDir}) creates empty before each test and
deletes afterwards, so every test starts from a known registry and never touches the registries in
the working directory. Reading and writing this file is local I/O, within the scope of the tests. Each test checks the endpoint bound to the call, the registry afterwards and whether
a deployment or an abort happened. Table~\ref{tab:eval-correctness} groups the situations by level.
All 46 resolver tests (23 per provider) and the two bootstrap tests pass.

The tests do not cover a registry file altered outside OmniFlow, but the code determines what
happens:

\begin{itemize}
  \item \textbf{File is not valid JSON:} the read fails and the deployment aborts.
  \item \textbf{Valid file without a \texttt{functions} object:} it is read as an empty registry,
  so every call goes to Levels~2 and~3.
  \item \textbf{Altered \texttt{url}:} harmless, because Level~1 looks the function up by its
  \texttt{serviceName} and overwrites the stored endpoint with the live one as drift (on AWS, an
  ARN whose region no longer resolves sends the call to rediscovery instead).
  \item \textbf{Altered \texttt{serviceName} naming another existing function:} not detected.
  Validation confirms that function, and the call is bound to it.
\end{itemize}

\noindent Only the last case goes undetected: the registry has no integrity protection
(Section~\ref{sec:concl-critical}).

\section{Methodology}
\label{sec:eval-methodology}

The benchmarks use the Java Microbenchmark Harness (JMH)~\cite{jmh} with the following settings
(\texttt{-f 3 -wi 3 -i 5 -w 1 -r 1}):

\begin{itemize}
  \item \textbf{Harness:} JMH 1.37 in \texttt{Average\allowbreak Time} mode, reporting
  microseconds per operation ($\mu$s/op).
  \item \textbf{Dead-code guard:} every result is passed to a \texttt{Blackhole}, a JMH object that
  consumes a value so that the JIT compiler cannot discard the computation that produced it.
  \item \textbf{Forks:} three separate JVM processes, so that one process's compilation and memory
  layout do not bias the result.
  \item \textbf{Warm-up:} three one-second iterations per fork, discarded, so that the code is
  measured after the JIT compiler has optimised it.
  \item \textbf{Measurement:} five one-second iterations per fork; each value is the mean of the
  fifteen.
  \item \textbf{Machine:} a laptop with an Apple M5 processor (10 cores) and 24\,GB of memory,
  running macOS, idle but not dedicated.
  \item \textbf{Precision:} the 99.9\% confidence interval is under 1\% of the score for half the
  measurements and under 6\% for nine in ten; the few noisy points are marked in
  Appendix~\ref{app:benchmarks}.
\end{itemize}

The experiments keep their benchmark-suite identifiers: T1--T14 for resolution and the registry,
S1 for packaging size. The symbols they vary are defined in Table~\ref{tab:eval-notation}.

Two kinds of resolver are measured. T1, T2, T4, T5 and T10--T14 use a reference resolver written
for the benchmarks, in two variants: one re-reads the registry on every internal call, the other
reads it once. It resolves calls from the registry as OmniFlow does but never validates a hit
against the provider, so it measures only the registry and the traversal of the workflow's steps.
It is used for two reasons. First, the production resolvers validate every registry hit against
the provider, so measuring them means either sending network requests, which the evaluation
excludes, or replacing the provider with a test double, and the point where the double replaces it
changes how much local work is measured (T6 and T7 replace it at different points). The reference
resolver measures the resolution alone, in the same way for both providers. Second, the production
resolvers only read the registry once, so comparing the two ways of reading it needs two resolvers
that differ only in that respect. Both variants produce the same resolved workflow, so the
difference measured between them comes from the registry reads alone.
T3 calls the registry store directly, without a resolver. T6 and T7 measure the production resolvers
(\texttt{Aws\allowbreak Internal\allowbreak Function\allowbreak Resolver} and
\texttt{Workflow\allowbreak Internal\allowbreak Function\allowbreak Resolver}), the classes
OmniFlow runs when it deploys a workflow (Section~\ref{sec:eval-real-resolvers}).

\label{sec:eval-resolution}

registry size.

\paragraph{Resolution costs one registry read plus a small constant per internal call (T1).}
T1 resolves, with the reference resolver, a workflow of $N$ calls, all internal or all external,
against a one-entry registry ($R{=}1$; Figure~\ref{fig:eval-t1}, with the values in
Table~\ref{tab:eval-t1}, Appendix~\ref{app:benchmarks}). Both variants pay one registry read,
about $10.7\,\mu$s, which the resolver performs before it traverses the workflow's steps, so both
lines of the figure start from the same point. A workflow without internal calls skips resolution entirely: the
provider deployers (\texttt{Google\allowbreak Cloud\allowbreak Deployer} and
\texttt{Amazon\allowbreak Cloud\allowbreak Deployer}, Chapter~\ref{cha:impl}) do not call the
resolver.
Each internal call then adds about $0.23\,\mu$s, the slope of the internal line, for three
in-memory operations:

\begin{itemize}
  \item \textbf{Lookup:} the function's name is looked up in the snapshot, a hash map, so the cost
  does not depend on $R$;
  \item \textbf{URL split:} the stored URL is split into the \texttt{host} and \texttt{path} fields
  of the call;
  \item \textbf{Rebuilt call node:} a copy of the call is built with that endpoint, since the
  workflow model is immutable.
\end{itemize}

\begin{figure}[!htb]
  \centering
  \includegraphics[width=0.7\textwidth]{images/benchmarks/T1_resolution_overhead.png}
  \caption{T1: resolution time, internal against external calls.}
  \label{fig:eval-t1}
\end{figure}

\noindent An external call skips all three: the resolver sees that it has no
\texttt{internalFunction} and keeps it unchanged, for about $0.005\,\mu$s, so the external line
stays almost flat. A workflow of 200
internal calls costs $56.4\,\mu$s. External calls add no registry work (T11, T12), and neither nesting depth nor parallel
width matters beyond the number of internal calls (T13, T14).

\paragraph{Reading the registry once removes the calls-times-size product (T2--T5).}
Re-reading the registry on every internal call, as the store's per-call methods do, costs $I$ reads
of an $R$-entry file; a single read per resolution replaces them with one read plus a small constant
per call. The benefit is expected;
the measurements give its size: up to $200\times$ at $N{=}200$, $R{=}1000$ (T3), and
$26$--$58\times$ on real workflows (T4, T5). Figure~\ref{fig:eval-t5} shows T5, where the
reference resolver resolves a workflow of 50 calls to ten functions ($N{=}50$, $F{=}10$) as the
registry grows: the per-call read (``without cache'' in the chart) and the single read (``with
cache'') both grow with $R$, and the gap between them widens.

\begin{figure}[!htb]
  \centering
  \includegraphics[width=0.7\textwidth]{images/benchmarks/T5_resolution_by_registry.png}
  \caption{T5: resolution time against registry size, per-call read against single read.}
  \label{fig:eval-t5}
\end{figure}

\noindent When the registry keys include the region
(\texttt{region/name}) but the call gives only the name, the exact lookup misses and the resolver
scans every key of the loaded map for one ending in \texttt{/name}. This costs at most
$1.95\times$ the exact lookup: $391\,\mu$s for 50 lookups at $R{=}1000$, under $8\,\mu$s per
call (T10).

\section{Cost of the Production Resolvers and of Registry Writes}
\label{sec:eval-real-resolvers}

\paragraph{Production resolvers (T6, T7).}
Both production resolvers use the single read and show the same shape: one read plus a constant
per call, $0.07$--$0.14\,\mu$s on AWS and about $0.95\,\mu$s on GCP. A workflow of 200 internal
calls to ten distinct functions costs $29.1\,\mu$s on AWS and $199.1\,\mu$s on GCP. Neither reaches
the provider. T6 replaces the whole Lambda inspector, so it excludes the SDK's local work; T7 keeps
the real Cloud Run inspector and replaces only its HTTP client, so request building, token handling
and JSON parsing are measured. This, and the URL split, is why GCP costs more. Either way, a validation's local work is
about a microsecond, against a network round-trip (Section~\ref{sec:eval-api-calls}).

\paragraph{Registry writes (T8, T9).}
Every \texttt{put()} reads the whole file, adds the entry and writes the whole file back, so one
write costs more the larger the registry: from $45\,\mu$s on an empty registry to $490\,\mu$s at
1\,000 entries (T8). Writing therefore costs more than resolving, which only reads the file: a
read with one lookup costs $10.5\,\mu$s on a one-entry registry and $183\,\mu$s at 1\,000 entries
(T2). The resolvers register each function with its own \texttt{put()}, so registering $K$
functions reads and rewrites the file $K$ times, and the time grows linearly with $K$: 100 writes
take 5.9\,ms on an empty registry and 36\,ms at 1\,000 entries. The bootstrap, which builds a
missing registry, writes all its entries at once. A lookup through the store before each write adds another full
read, $26$--$62\%$ more (T9). The production resolvers avoid it by looking calls up in the snapshot.
The most expensive case measured, 100 miss-then-write pairs on a 1\,000-entry registry, takes
$59$\,ms.

\section{Provider API Calls per Resolution}
\label{sec:eval-api-calls}

The benchmarks do not include network traffic, so Table~\ref{tab:eval-api-calls} counts, from the
code, the provider requests each ladder path sends. $G$ is the number of candidate regions (the
regions enabled for the AWS account, or the Cloud Run locations of the GCP project). If the
registry has an entry for the called function, the resolver confirms with the provider that the
function still exists and reads its current endpoint. It does this for every internal call, not once per function: the
snapshot avoids re-reading the registry file, but it does not record which functions the provider has already confirmed. A
workflow with $I$ internal calls to the same function therefore sends $I$ validation requests. The
resolver fetches the list of regions from the provider only when a call first needs to search
them, and at most once per deployment. The search sends up to one request per region, and only
two kinds of call need it: those whose function is not in the registry, and those whose entry points to
a function that no longer exists.

The region list costs one EC2 \texttt{Describe\allowbreak Regions} on AWS, or one Cloud Run

upload, creation and polling until active), whose request count depends on how long the provider
takes, so it has no fixed count.

A deployment of $I$ internal calls therefore sends between $I$ requests, when every call hits a
valid entry, and $1 + I \cdot G$, when the registry is empty and references are bare names. The
registry keeps the count linear in $I$; a region-qualified reference does the same for a call that
misses.

\section{Discussion}
\label{sec:eval-discussion}

\paragraph{Answer to RQ1.}
In every situation of Table~\ref{tab:eval-correctness}, both resolvers take the expected decision:
each call is bound to the registered, current or discovered endpoint, and a function is deployed
only when it is in neither the registry nor any region and every region could be checked. Stale
entries, ambiguous names and inaccessible regions abort the resolution instead of binding a guess
or deploying a duplicate. The answer is positive for the resolution logic on both providers, with
the evidence coming from tests that simulate the provider.

\paragraph{Answer to RQ2.}
Locally, resolution costs one registry read plus about $0.23\,\mu$s per internal call. Reading the registry
once instead of per call removes the product of calls and registry size, a speedup of up to
$200\times$. The production resolvers take $29\,\mu$s (AWS) and $199\,\mu$s (GCP) for a workflow
of 200 internal calls. The cost follows the number of internal calls, not external calls or the shape of the
workflow. On the provider side, resolution sends one request per internal call when the registry
is current, and up to one per candidate region for each call that must be discovered.

\paragraph{Global framing.}
All measured costs lie between microseconds and, for the worst write case, $59$\,ms. They are the
local part of resolution only; the network requests are counted, not timed. Resolution is not the
bottleneck of a deployment: the cloud deployment itself takes minutes.

\section{Threats to Validity}
\label{sec:eval-threats}

\begin{itemize}
  \item \textbf{One laptop:} the absolute values belong to that machine. Since file I/O dominates
  several experiments, slower storage would raise every read and write, but the shape of each cost
  and the relationships between experiments, measured under the same conditions, would hold.
  \item \textbf{Later sessions:} T1, T6 and T7 were measured in later sessions, with the same
  settings on the same machine. T1 was run twice: one registry read took $9.8\,\mu$s in the first
  run and $10.7\,\mu$s in the second, about 10\% apart. Differences of that size between these
  three experiments and the others may come from the change of session rather than from the code
  being measured.
  \item \textbf{Provider replaced by test doubles:} the tests show that each resolver decides
  correctly given what the provider reports, not that the real APIs report what the doubles
  assume. The case study (Section~\ref{sec:case-artifacts}) checks this on both providers for the
  bootstrap, Levels~2 and~3 and validated Level~1 hits.
  \item \textbf{Aborts not tested on the real providers:} the situations in which resolution
  aborts (stale entries, ambiguous names and inaccessible regions) were tested only with test
  doubles, not against the real APIs; testing them is future work (Section~\ref{sec:concl-future}).
\end{itemize}
